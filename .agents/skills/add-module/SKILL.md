name: add-module
description: Design and add a new RMS module or bounded context with a coherent purpose, ownership boundary, public contract, dependencies, profiles, and conformance evidence.

# Add a Module

1. Establish the project before design. In a brand-new directory, run `rms init <path> --name <system-name> --purpose "<purpose>"`, then make the authorized bootstrap commit prescribed by its output. Without commit authority, stop at exactly `bootstrap prepared; provenance baseline pending authorized commit`. In an initialized or unfamiliar checkout, run `rms check --environment`; do not call `rms design` while `.rms/config.yaml` is absent or environment readiness is non-passing.
2. Confirm that a new boundary is justified by distinct language, ownership, invariants, change cadence, or replaceability. Do not create a module for every noun.
3. After initialization and its authorized bootstrap commit, begin with `rms design --root <root> --task "<exact user task>" --ai`; use typed intent flags for CI or offline input. Resolve every material `unknown`; deterministic RMS policy, not task keywords or provider advice, chooses the topology.
4. Follow exactly one design action with its returned `--route-receipt <RUN_ID>`: `rms add-module` for a standalone owner or `rms add-capability-tree` for an explicitly recommended composite tree. `add-capability-tree` never means “publish a capability” and never infers a surface from purpose prose; pass `--surface` only when the typed model requires one. Its generated domain command and reusable capability have distinct stable identities, and the boundary requires the exact capability-kind provider contract. A pure reusable library is an ordinary standalone `domain-engine`, with no exception. Only one runnable module mixing invariant-bearing decisions and boundary effects needs `unsplit_runnable_justification`.
5. Choose whether the new unit is a bounded context, internal module, runtime monitor, workflow, adapter, or library.
6. Define:
   - one-sentence purpose;
   - authoritative terminology;
   - owned concepts, data, identities, and decisions;
   - public commands, queries, events, APIs, or capabilities;
   - required capabilities and contracts;
   - important invariants;
   - declared effects;
   - compatibility policy.
   - versioned artifacts and transformations when data changes form or crosses a boundary;
   - public protocol automata when several modules participate in one ordered conversation;
   - resource ownership automata when handles, files, memory, locks, transactions, processes, devices, or similar lifetimes affect correctness;
   - privileged, unsafe, or foreign authority boundaries;
   - executable temporal properties for always, eventually, precedence, exclusion, at-most-once, or bounded-response promises, using typed public observations, explicit assumptions, and dimensionally valid metric bounds.
7. Declare the Core profile and only the additional profiles that actually apply.
8. Choose the strongest representation the implementation language supports:
   - closed sets of domain meaning: algebraic data types, sealed variants, or enums;
   - values with validity rules: opaque types, validated constructors, or smart constructors;
   - expected domain failures: explicit result types rather than ambient exceptions;
   - untrusted or versioned input: runtime schemas and boundary validators;
   - query/projector output: read models or result structs may omit public constructors only when the implementation binding declares `architecture.allowed_missing_constructors` and evidence names the producing query/projector;
   - lifecycle/order-dependent behavior: a state model, transition table, or state machine.
9. Treat representation as a first-class role: closed variants, validated values, commands, states, events, result/rejection types, message envelopes, transition outputs, transition records, and boundary schemas belong in explicit language-idiomatic units.
10. Keep pure transitions separate from representation definitions, and keep boundary parsing separate from both. Binding container names belong under `architecture.machine.types`; semantic lists contain actual alternatives, never container names. Stateful, boundary, workflow, storage, integration, and projection machines use one `transition(state, input)` path where the input ADT closes over commands, observed events, and effect results. Every transition declares a stable semantic `case`; multiple outcomes for the same state/input are separate cases, and replay evidence uses the same source-branch name. Transitions return next state, emitted events, commands, effects, and reply. When replacing generated role code, use RMS apply so `architecture.roles`, `architecture.machine`, `architecture.representation`, and semantic revision proof stay aligned.
11. Do not introduce a state machine only because a record has a status field. Use one when legal commands, facts, or invariants depend on lifecycle order. Generated capability contracts are scaffold obligations, not product semantics: replace each one through `rms spec apply` with `contracts.set`, including `direction: provided` for owned surfaces or `direction: required` for consumer expectations, product-specific meaning, accepted inputs, guaranteed outcomes, and explicit rejection categories, before implementation. Never publish a required dependency with `contracts.add` merely to make it editable. After scaffolding, use `rms spec apply` for new laws, contracts, machine variants, transitions, semantic roles, public entrypoints, and evidence obligations rather than hand-creating architecture files. Use `set` and `remove` to revise RMS semantics; spec apply automatically closes every active revision and hash-seals the new record. Use explicit `supersedes` only for additional non-local branches, and never edit or delete applied records. Use `rms machine apply` only for focused inner-machine edits after the semantic layer is correct.
12. Run `rms spec apply ... --dry-run` before code. Inspect `final_machine`, `final_semantic_functions`, `final_public_behavior_bindings`, and `final_dependency_behavior_bindings`; do not proceed while machine cases remain generic, real branches are omitted, an invariant lacks its authority owner, a public behavior lacks one contract-to-function-to-machine path, or a required capability lacks one exact consumer-to-provider path. Change exact function symbols, purity, discharged promises, assumptions, and evidence through `semantic_functions.add/set/remove`; change the two cross-layer paths through `public_behavior_bindings` and `dependency_behavior_bindings`, never direct manifest editing.
    - Never repair `module.yaml`, `implementation.yaml`, contracts, roles, surfaces, or evidence declarations by direct editing. Keep `surfaces.set: null` for unrelated incremental changes and remove intentional surfaces explicitly by name. If the required semantic operation is not expressible by RMS, stop and report the CLI gap instead of bypassing it.
    - Treat the rendered RMS plan schema as self-contained. Prefer `set` for complete scaffold replacement and `add`/`remove` for incremental changes; do not inspect sibling projects, prior dogfood runs, RMS source, or generated examples outside the project to infer the schema or borrow semantics.
13. Runnable app, UI, browser, CLI, HTTP, batch, and executable surfaces must be declared with `rms surface apply` or `rms spec apply`, delegate to an existing role or concrete symbol, declare boundary effects or a precise no-effect justification, and name both a concrete `usage_document` and a `smoke_command` key from implementation commands. `rms verify` executes the smoke command. For browser surfaces, distinguish the inspectable controller `entrypoint` from the host `launch_entrypoint`; any local script loaded by the host is also part of the surface and must import/call the declared controller or adapter, not duplicate parser/generator/transition/domain logic in a second bundle.
14. Reusable domain/library modules publish meaning through `rms spec apply`: `contracts.add kind: capability direction: provided` plus the matching `public_behavior_bindings` entry in the same final change. Required capabilities use `direction: required` plus a dependency behavior binding. Keep one public facade, package/reuse evidence, and no consumer imports of private roles. This semantic publication never creates a module tree.
15. Define the consistency boundary, lifecycle, legal transitions, concurrency, persistence, and migration only if the Stateful profile applies. Illegal transitions must be rejected or made unrepresentable.
16. Define retry, timeout, ordering, duplicate handling, and reconciliation only if the Distributed profile applies.
17. For each effect, declare its result alternatives, atomicity, executor role, and exact executor symbol. Atomicity is evaluated per protocol: an aggregate executor may iterate only with `atomicity: aggregate`, justification, and evidence. The executor role names the exact effect and uses a dedicated path separate from transition and machine-driver code; it is also an effectful `effect-executor` semantic function. Shared IO mechanics used by multiple executors belong in a private `effect_support` role, which may not own state progression, call transitions/drivers, or serve as a runnable/public facade. If one result can change the next decision, emit one request, execute it once, and feed one typed result back through the canonical transition. Effectful stateful machines declare exact driver and transition-record functions in their machine and role bindings; effect-emitting runnable surfaces delegate to an exact callable that reaches the driver. The driver retains complete records, advances from each record's state, and owns the complete repeated transition/effect/result cycle even when public and machine command names differ. Executors never own retry, compensation, stop/continue policy, or state progression. Every declared message envelope must have a binding-native representation. Define coordination state, deadlines, terminal states, subscription registry, retry count, golden timelines, and compensation only if the Workflow profile applies.
18. Define observed inputs, derived facts or streams, trigger conditions, monitor authority, retrigger/idempotency policy, and failure mode only if the Monitor profile applies.
19. Add law, contract, scenario, boundary, property, fuzz, runtime, and package/reuse evidence as applicable. Broad laws that say always, never, bounded, ordered, normalized, parsed, generated, impossible, or must not happen should have semantic properties with input spaces, oracles, evidence, and counterexample replay policy. Label realizations truthfully: fixed examples are `deterministic-corpus`, complete finite enumeration is `deterministic-exhaustive`, generated cases are `generated-property`, coverage-guided execution is `coverage-fuzzer`, and oracle-strength campaigns are `mutation-tester`. Every realization names an exact runner; generated-property and deterministic-exhaustive strategies also name an exact generator. The runner calls the generator, semantic operation, and oracle. Property evidence generated by spec apply is an obligation until that exact realization executes.
    - Derive the hunt posture from risk: generated or exhaustive checks for pure/numeric decisions, finite exploration for machines/workflows, coverage fuzzing for boundary/storage/external results, schedule/fault exploration for distributed behavior, analyzer or sanitizer lanes for unsafe/foreign authority, mutation testing for reusable semantic oracles, and real-trace evaluation plus violation search for temporal promises.
    - Put expensive runners in the `nightly` profile and attach canonical probe searches through `explorations`. Use `verification.hunt_exceptions` only when an obligation is genuinely inapplicable, naming the closed obligation and a focused reason.
20. Include negative evidence for impossible variants, invalid constructors, malformed boundary input, illegal transitions, typed rejections, transition records, replay bundles, first-bad-transition diagnostics, generated property cases, replayable counterexamples, and monitor trigger/non-trigger cases when applicable. Do not hand-author active traces: declare a producer, call the real transition-record path, then use `rms trace run --record`. Each record must match the canonical case's exact state change and outputs. Replace scaffold contracts and placeholder evidence before declaring the module implemented.
21. Update the system manifest, context map, and glossary index.
22. Validate that no existing owner now has overlapping responsibility with `rms validate --root <root>` and `rms compose --root <root>`.
