name: add-module
description: Design and add a new RMS module or bounded context with a coherent purpose, ownership boundary, public contract, dependencies, profiles, and conformance evidence.

# Add a Module

1. Run `rms diagnose` when starting from an unfamiliar checkout.
2. Confirm that a new boundary is justified by distinct language, ownership, invariants, change cadence, or replaceability. Do not create a module for every noun.
3. Use `rms design --root <root> --task "<task>"` first when module boundaries or semantic shapes are unclear. In a fresh project created from product intent only, treat boundaries as unclear until design has proposed the module tree. Treat deterministic design hints as the scaffold decision: if they recommend a recursive capability, use `rms add-capability`; do not substitute one module for convenience. Choose implementation bindings before scaffolding code. Omit bindings only for an intentionally semantic-only result. Use a single module only for explicit library-only intent or a canonically recorded single-module exception.
4. Use `rms add-capability <path> --name <name> --purpose "<purpose>" --domain-binding <binding> --boundary-binding <binding>` when the requested capability should be implemented as a recursive tree with a composite parent, domain child, and boundary child, especially when the intent combines user/boundary interaction, lifecycle decisions, and effect simulation or external-service coordination. Omit `--domain-child` and `--boundary-child` unless the user supplied semantic child names; do not invent `-rules`, `-engine`, `-adapter`, `-cli`, `-web`, or binding-specific child names just to describe roles. If an intentionally semantic-only module later gains code, run `rms add-binding <module.yaml> --binding <rust|swift|js|executable>` instead of creating a scratch module or copying generated files. For app, tool, CLI, local-first reference app, runnable, or smoke-test intents, declare a runnable surface through RMS unless the user explicitly requested a library-only package. Use `rms add-module <path> --name <name> --purpose "<purpose>" --binding <binding>` when the CLI can scaffold one requested shape. Use `--shape domain-engine`, `--shape boundary-adapter`, `--shape runtime-monitor`, `--shape workflow`, `--shape storage-adapter`, `--shape integration-adapter`, or `--shape composite` to record semantic role obligations. Refine the generated artifacts rather than maintaining parallel agent-only scaffolding.
5. Choose whether the new unit is a bounded context, internal module, runtime monitor, workflow, adapter, or library.
6. Define:
   - one-sentence purpose;
   - authoritative terminology;
   - owned concepts, data, identities, and decisions;
   - public commands, queries, events, APIs, or capabilities;
   - required capabilities and contracts;
   - important invariants;
   - declared effects;
   - compatibility policy.
7. Declare the Core profile and only the additional profiles that actually apply.
8. Choose the strongest representation the implementation language supports:
   - closed sets of domain meaning: algebraic data types, sealed variants, or enums;
   - values with validity rules: opaque types, validated constructors, or smart constructors;
   - expected domain failures: explicit result types rather than ambient exceptions;
   - untrusted or versioned input: runtime schemas and boundary validators;
   - query/projector output: read models or result structs may omit public constructors only when the implementation binding declares `architecture.allowed_missing_constructors` and evidence names the producing query/projector;
   - lifecycle/order-dependent behavior: a state model, transition table, or state machine.
9. Treat representation as a first-class role: closed variants, validated values, commands, states, events, result/rejection types, message envelopes, transition outputs, transition records, and boundary schemas belong in explicit language-idiomatic units.
10. Keep pure transitions separate from representation definitions, and keep boundary parsing separate from both. Binding container names belong under `architecture.machine.types`; semantic lists contain actual alternatives, never container names. Stateful, boundary, workflow, storage, integration, and projection machines use one `transition(state, input)` path where the input ADT closes over commands, observed events, and effect results. Every transition declares a stable semantic `case`; multiple outcomes for the same state/input are separate cases, and replay evidence uses the same source-branch name. Transitions return next state, emitted events, commands, effects, and reply. When replacing generated role code, use RMS apply so `architecture.roles`, `architecture.machine`, `architecture.representation`, and semantic revision proof stay aligned.
11. Do not introduce a state machine only because a record has a status field. Use one when legal commands, facts, or invariants depend on lifecycle order. Generated capability contracts are scaffold obligations, not product semantics: replace each one through `rms spec apply` with `contracts.set`, including `direction: provided` for owned surfaces or `direction: required` for consumer expectations, product-specific meaning, accepted inputs, guaranteed outcomes, and explicit rejection categories, before implementation. Never publish a required dependency with `contracts.add` merely to make it editable. After scaffolding, use `rms spec apply` for new laws, contracts, machine variants, transitions, semantic roles, public entrypoints, and evidence obligations rather than hand-creating architecture files. Use `set` and `remove` to revise RMS semantics; spec apply automatically closes every active revision and hash-seals the new record. Use explicit `supersedes` only for additional non-local branches, and never edit or delete applied records. Use `rms machine apply` only for focused inner-machine edits after the semantic layer is correct.
12. Run `rms spec apply ... --dry-run` before code. Inspect both `final_machine` and `final_semantic_functions`; do not proceed while machine cases remain generic, real branches are omitted, or an invariant lacks its declared authority owner. Change exact function symbols, purity, discharged promises, assumptions, and evidence through `semantic_functions.add/set/remove`, never direct manifest editing. Public commands in `module.yaml` must be represented by the declared implementation machine, parser, adapter, transition, representation, or semantic functions.
    - Never repair `module.yaml`, `implementation.yaml`, contracts, roles, surfaces, or evidence declarations by direct editing. Keep `surfaces.set: null` for unrelated incremental changes and remove intentional surfaces explicitly by name. If the required semantic operation is not expressible by RMS, stop and report the CLI gap instead of bypassing it.
    - Treat the rendered RMS plan schema as self-contained. Prefer `set` for complete scaffold replacement and `add`/`remove` for incremental changes; do not inspect sibling projects, prior dogfood runs, RMS source, or generated examples outside the project to infer the schema or borrow semantics.
13. Runnable app, UI, browser, CLI, HTTP, batch, and executable surfaces must be declared with `rms surface apply` or `rms spec apply`, delegate to an existing role or concrete symbol, and declare boundary effects or a precise no-effect justification. For browser surfaces, distinguish the inspectable controller `entrypoint` from the host `launch_entrypoint`; any local script loaded by the host is also part of the surface and must import/call the declared controller or adapter, not duplicate parser/generator/transition/domain logic in a second bundle.
14. Reusable domain/library modules must declare reusable meaning in RMS first: `provides.capabilities[]` with a contract, one public facade in `implementation.yaml`, package/reuse evidence, and no consumer imports of private role files. RMS says what is reusable; native package manifests only say how a binding imports the declared facade.
15. Define the consistency boundary, lifecycle, legal transitions, concurrency, persistence, and migration only if the Stateful profile applies. Illegal transitions must be rejected or made unrepresentable.
16. Define retry, timeout, ordering, duplicate handling, and reconciliation only if the Distributed profile applies.
17. For each effect, declare its result alternatives, atomicity, executor role, and exact executor symbol. The executor role names the exact effect and uses a dedicated path separate from transition and machine-driver code; it is also an effectful `effect-executor` semantic function. If one result can change the next decision, emit one request, execute it once, and feed one typed result back through the canonical transition. Effectful stateful machines declare exact driver and transition-record functions in their machine and role bindings; effect-emitting runnable surfaces delegate to an exact callable that reaches the driver. The driver retains complete records, advances from each record's state, and owns the complete repeated transition/effect/result cycle even when public and machine command names differ. Executors never own iteration, retry, compensation, stop/continue policy, or state progression. Every declared message envelope must have a binding-native representation. Define coordination state, deadlines, terminal states, subscription registry, retry count, golden timelines, and compensation only if the Workflow profile applies.
18. Define observed inputs, derived facts or streams, trigger conditions, monitor authority, retrigger/idempotency policy, and failure mode only if the Monitor profile applies.
19. Add law, contract, scenario, boundary, property, fuzz, runtime, and package/reuse evidence as applicable. Broad laws that say always, never, bounded, ordered, normalized, parsed, generated, impossible, or must not happen should have semantic properties with input spaces, oracles, evidence, and counterexample replay policy. Boundary, storage, integration, and runnable parser surfaces should have fuzz-style semantic targets or a concrete no-fuzz justification. Label realizations truthfully: fixed examples are `deterministic-corpus`, complete finite enumeration is `deterministic-exhaustive`, generated cases are `generated-property`, and coverage-guided execution is `coverage-fuzzer`. Every non-corpus realization names an exact relative binding `path#symbol` harness. Property evidence generated by spec apply is an obligation until the executed command and observed result replace it. Bindings realize these obligations, but RMS owns the property meaning.
20. Include negative evidence for impossible variants, invalid constructors, malformed boundary input, illegal transitions, transition records, replay bundles, first-bad-transition diagnostics, generated property cases, replayable counterexamples, and monitor trigger/non-trigger cases when applicable. Every lifecycle state must be reachable from the declared initial state. Every canonical case must occur in declared transition source, and replay provenance must name that source file and exact case rather than an evidence artifact. Replace scaffold contracts and placeholder evidence before declaring the module implemented; `rms validate --root <root>` should not report `semantic.contract-scaffold-active`, `evidence.placeholder`, `evidence.bootstrap-active`, `evidence.source-unpinned`, or `evidence.semantic-shape-only` for implemented modules. Evidence must not claim a current filesystem snapshot or missing Git revision; strict audit resolves the committed candidate revision.
21. Update the system manifest, context map, and glossary index.
22. Validate that no existing owner now has overlapping responsibility with `rms validate --root <root>` and `rms compose --root <root>`.
